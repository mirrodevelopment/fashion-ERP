1. CRITICAL BUGS (P0)
--------------------------------------------------------------------------------

[BUG-P0-01] GarmentService.create() Injected Fake Fallback Business Data
- File: src/main/java/com/fashionerp/garment/GarmentService.java
- Problem:
    When requests lacked certain fields, create() silently inserted hardcoded
    dummy data ("ORD-2026-CUSTOM", "Walk-in Client", "Bridal 2026", "Sneha",
    "Aishwarya", "Haulo Boutique - Main Branch", "../assets/designs/zari-bloom-front.jpg",
    amount 10,000) permanently into the PostgreSQL database.
- Fix:
    Removed all synthetic business fallbacks. Enforced validation rejecting
    requests missing required fields (customerName, orderCode, totalAmount)
    with IllegalArgumentException. Kept only safe operational defaults (e.g.,
    productionStage = "Designing").

[BUG-P0-02] GarmentService.toDetailResponse() Returned Static Mock Data
- File: src/main/java/com/fashionerp/garment/GarmentService.java
- Problem:
    GET /api/v1/garments/{id} returned hardcoded static lists of materials
    ("Raw Silk", "Organza Lining", "Zari Border"), fixed 36" bust measurements,
    and a fake Sept 2026 trial timeline for every single garment viewed.
- Fix:
    Replaced hardcoded static lists with empty lists (new ArrayList<>()) so no
    fabricated data is presented to staff or clients. Real cross-entity queries
    can populate these lists cleanly.

[BUG-P0-03] api.js: collections Namespace Defined Twice
- File: front end/api.js
- Problem:
    The collections namespace was defined twice on window.api (L265-L276 and
    L419-L489). In JavaScript object literals, the second key silently clobbered
    the first, causing api.collections.page() and api.collections.toggleArchive()
    to throw "TypeError: api.collections.page is not a function" at runtime.
- Fix:
    Removed the duplicate initial block and merged page() and toggleArchive()
    directly into the canonical api.collections namespace.

[BUG-P0-04] api.js: garments.kpis() Returned Fabricated Mock Fallback
- File: front end/api.js
- Problem:
    api.garments.kpis() returned hardcoded fallback figures (248 total, 72 in
    production, 28 in trial, 16 in QC, 46 ready, 86 delivered) if the backend
    call failed, masking API failures and displaying false metrics.
- Fix:
    Replaced fake numbers with zeroed-out defaults (0).

[BUG-P0-05] GarmentService.getKpis() Returned Fabricated Delta Strings
- File: src/main/java/com/fashionerp/garment/GarmentService.java
- Problem:
    getKpis() synthesized hardcoded delta strings ("up 12% vs last month",
    "up 27% vs last month", etc.) as factual analytics without historical data.
- Fix:
    Removed fabricated delta strings, returning null/zero so frontend renders N/A.

[BUG-P0-06] PaymentService.recordTransaction() Subtracted Balances Without Validation
- File: src/main/java/com/fashionerp/payment/PaymentService.java
- Problem:
    recordTransaction() subtracted amount directly from customer balance and added
    to paidAmount without validating if amount was positive or if existing
    balance/paidAmount was null, risking NullPointerException and negative balance corruption.
- Fix:
    Validated amount > 0, added null-safety defaulting null paidAmount and balance
    to BigDecimal.ZERO before performing arithmetic.

[BUG-P0-07] OrderService and InventoryService Code Generation Race Condition
- Files:
    - src/main/java/com/fashionerp/order/OrderService.java
    - src/main/java/com/fashionerp/inventory/InventoryService.java
    - src/main/java/com/fashionerp/inventory/InventoryRepository.java
- Problem:
    generateCode() relied on count() + 1. Under concurrent requests, two transactions
    reading the same count generated identical codes (e.g. ORD-2026-0005 or ITEM-0004),
    causing unique constraint violations and HTTP 500 crashes.
- Fix:
    Added existsByItemCode() to InventoryRepository. Implemented collision-checking
    while loops in both services and added synchronized protection.

    to OrderStatus.READY, and initial stages (ORDER, ORDER_PLACED, DESIGN, DESIGNING)

    adjust() added quantity to stockQty directly without checking if the result was
    negative, allowing stock levels to drop below 0 (e.g., -40m).
- Fix:

    quantity to drop below zero.

[BUG-P1-04] CollectionService archived Filter Precedence Bug
- File: src/main/java/com/fashionerp/collection/CollectionService.java
- Problem:
    Passing archived=true unconditionally overwrote the status parameter,
    preventing combined or refined filtering.
- Fix:
    Updated logic so archived=true only defaults status to "ARCHIVED" if no explicit
    status parameter was provided.

[BUG-P1-05] MeasurementController.kpis() Performed In-Memory Full-Table Scans
- Files:
    - src/main/java/com/fashionerp/measurement/MeasurementController.java
    - src/main/java/com/fashionerp/customer/CustomerBodyMeasurementRepository.java
- Problem:
    kpis() loaded the entire body_measurements table into heap memory 3 times
    using findAll().stream().filter(...), causing excessive memory allocation and latency.
- Fix:

      - countDistinctCustomerByIsCurrentTrue()
      - countDistinctCustomerWithVersionGreaterThanOne()
      - countCurrentByGarmentType()
    Refactored MeasurementController.kpis() to use these fast database-side queries.

[BUG-P1-06] TrialService Trial Code Collision Risk
- File: src/main/java/com/fashionerp/trial/TrialService.java
- Problem:
    Trial codes were formatted as "TRL-" + yyyyMMddHHmmss. Multiple trial bookings
    within the same second produced identical codes.

[BUG-P1-07] Null Revenue Sums in OrderController and PaymentController KPIs
- Files:
    - src/main/java/com/fashionerp/order/OrderController.java
    - src/main/java/com/fashionerp/payment/PaymentController.java

    sumPaidAmount() and sumThisMonthPaidAmount() return null on empty tables or months,
    causing JSON responses like {"totalRevenue": null} which crashed frontend calculations.
- Fix:
    Wrapped all revenue sums with null-safe checks defaulting to BigDecimal.ZERO.

[STAGE-01] Strict Invariant: Stage 1 = ORDER_TAKEN, Final Stage = READY_TO_DELIVER
- Target: Production Room Kanban & Workflow Blueprint Configuration

- Problem:
    In the stage_definitions table, sort orders were misaligned (DESIGNING and ORDER_TAKEN
    both had sort_order 1; READY_TO_DELIVER had sort_order 2). As a result, the Production Room
    Kanban displayed "Ready to Deliver" as the 3rd column before Cutting, Stitching, and QC.
- Implementation & Resolution:
    1. Database: Assigned canonical sequential order (1: ORDER_TAKEN, 2: DESIGNING,
       3: CUTTING, 4: STITCHING, 5: EMBROIDERY, 6: FINISHING, 7: QC, 8: READY_TO_DELIVER).
       Updated seed_all_fields.sql for persistent baseline replication.
    2. Backend Service (StageDefinitionService.java):
       - Added enforceBoundarySort() helper wrapping listActive() and listAll() to guarantee
         that ORDER_TAKEN is strictly at index 0 (sort_order = 1) and READY_TO_DELIVER is strictly
         at the last index (sort_order = N), with intermediate stages sorted between.
       - Hardened reorder(): Automatically sanitizes incoming UUID arrays, moving ORDER_TAKEN
         to index 0 and READY_TO_DELIVER to the final index regardless of client payload.
       - Hardened create(): Enforces sort_order >= 2 for new stages and pushes READY_TO_DELIVER
         to remain permanently at the end.
    3. Frontend (production.js):
       - Added defensive client-side boundary enforcement in loadStageDefinitions() ensuring
         ORDER_TAKEN is index 0 and READY_TO_DELIVER is the last element of STAGES before rendering.
- Verification:
    - Tested via test_reorder_boundary.ps1: Sent scrambled/reversed array with READY_TO_DELIVER
      at index 0 and ORDER_TAKEN at the end. Backend boundary enforcement successfully intercepted
      and re-established ORDER_TAKEN as Stage 1 and READY_TO_DELIVER as Stage 8.
    - Live Endpoint: /api/v1/production/stage-definitions?activeOnly=true confirmed returning
      Stage 1 (Order Taken) to Stage 8 (Ready to Deliver) in perfect sequence.

- Implementation & Architectural Details:
    1. Universal Algorithm Definition:
       - Multi-word names: First letter of first name + First letter of second name (e.g., "SIVASURYA S" -> "SS", "Ms. SIVASURYA S" -> "SS", "Ananya Sharma" -> "AS").
       - Single-word names (no second name exists): First 2 letters of name (e.g., "Priya" -> "PR", "Rahul" -> "RA", "Kavitha" -> "KA").
       - Automatic honorific cleaning: Common prefixes ("Ms.", "Mr.", "Mrs.", "Miss", "Dr.", "Prof.", "Smt.", "Shri") are filtered out so that actual customer initials are derived.
       - Deterministic HSL gradient palette selection based on customer name string hash.
    2. Global Core Engine (`fragments.js` & `fragments-inline.js`):
       - `window.getPatronInitials(name)`: Canonical implementation of the user's algorithm with fail-safe fallbacks.
       - `window.getPatronAvatarTheme(name)`: Deterministic glassmorphism theme generator matching Haulo dark luxury aesthetics.
       - `window.renderPatronAvatarHtml(name, avatarUrl, sizeClass, extraStyles)`: Renders either a verified image or the initials tile, complete with an inline `onerror` fallback reverting broken images back to initials tiles.
       - `window.applyPatronAvatarElement(containerEl, name, avatarUrl, sizeClass, extraStyles)`: Safely attaches the avatar into any DOM container.
    3. Global CSS Design Tokens (`nav.css`):
       - Added `.haulo-patron-avatar-initials`, `.haulo-patron-avatar-wrap`, `.haulo-avatar-xl` (80px), `.haulo-avatar-lg` (56px/68px), `.haulo-avatar-md` (40px/44px/48px), `.haulo-avatar-sm` (32px/36px), and `.haulo-avatar-xs` (26px/28px/30px).
